# FormFix AI

**Connected copy of the supplied frontend:** run `npm run dev:connected`, then open
http://localhost:5174. This starts the real local backend and uses explicitly labelled
recorded AI. See [backend connection instructions](docs/CONNECT_BACKEND.md) for setup,
durable Docker deployment, live Gemini configuration and the offline fallback.
The original frontend-only commands and design notes below remain as reference;
use `npm run dev:demo` for the browser-only fallback.

**Tell me what this form actually wants.**

FormFix takes a long, confusing form and turns it into a sequence of decisions: the original
question, a plain-language explanation in your language, the answer you enter, and the exact
place on the page the explanation came from — all visible at once.

This repository is the **frontend** plus the **shared contract** and the **shared fixtures**
that the backend build uses too.

---

## Run it

```bash
npm install
npm run fixtures:build   # regenerates the demo PDF and its measured regions
npm run dev              # http://localhost:5173
```

Then press **Try a sample form**.

Other commands:

```bash
npm run build       # typecheck + production build
npm run typecheck   # all workspaces
npm test            # component and integration tests (vitest)
npm run test:e2e    # end-to-end journeys (playwright, desktop + phone)
```

`npm run test:e2e` needs browsers once: `npx playwright install chromium`.

Requires Node 20.19 or newer. The lockfile is committed and every dependency is pinned exactly.

## The two modes

Set in `apps/web/.env` (see `.env.example`):

| `VITE_APP_MODE` | What answers requests |
|---|---|
| `demo` (default) | A deterministic fixture adapter running in a Mock Service Worker. Every screen shows a **Demo data** badge. No network, no AI provider, nothing leaves the browser. |
| `live` | The real backend at `VITE_API_BASE_URL`, proxied through the dev server at `/api`. |

**Live mode never falls back to fixtures.** The fixture adapter is behind a dynamic import
guarded by the mode check (`src/mocks/start.ts`), so in live mode the fixture code is not even
loaded — a failed request shows as a failure, never as a plausible-looking answer.

There are no provider keys in the browser and no direct AI or OCR calls from it. Everything
goes through one typed client, `apps/web/src/lib/api.ts`.

## The demo document

There was no real target form supplied, so the repository ships a **fictional** one:
*Sample Student Support Application — Demo Only*. Six pages, three sections, fourteen
questions, three document requirements. Every page is stamped **SYNTHETIC DEMONSTRATION
DOCUMENT — NOT AN OFFICIAL SCHEME**, and the app repeats that wherever the document is named.
It is not a real scheme and no institution issues it.

It is generated by `fixtures/demo/scripts/build-pdf.mjs`, which draws the PDF **and** emits the
normalised coordinates of every block in the same layout pass. Source highlighting is therefore
measured, not guessed. A real target form can replace it once its fields and rules have been
verified against the actual document.

The sample session deliberately starts part-filled with three mistakes, so the final check has
something honest to find:

1. a five-digit PIN where page 3 says six digits are required,
2. an empty supporting-document reference number that page 6 marks required,
3. one required document not marked as ready.

Correcting all three and re-running the check changes the result.

## What is implemented

- Upload with drag-and-drop and a keyboard-accessible picker, early type and size checks
  against server-reported limits, and a sample-document path.
- Analysis progress that shows the server's real stages (uploaded → extracting → structuring →
  ready), with `needs_review` and `failed` outcomes. Leaving the page does not cancel the job.
- A three-panel workspace on desktop (sections, field editor, original document) that collapses
  to Guide / Original / Ask tabs below 1024px, keeping the current question and any draft answer
  across a tab switch.
- Real PDF rendering with PDF.js, fit-to-width by default, zoom and rotation, and source
  highlights that stay aligned at every zoom level and rotation. Where the extractor has no
  region, the viewer opens the page and shows the quote instead of drawing a guessed rectangle.
- Field explanations in English, Hindi, Telugu and Marathi, cached per form, field, language and
  schema version, with stale language requests cancelled.
- A contextual chat drawer that cites its sources, distinguishes *answered*, *not found in the
  form* and *needs clarification*, supports retry and cancellation, and renders a restricted
  Markdown subset — never raw HTML.
- A document checklist with self-reported readiness, stated alternatives, conditional
  requirements, and the document-number field kept separate from possession.
- Deterministic validation grouped into must-fix, checklist gaps, warnings and manual review,
  with "Fix this" navigation and sources on every issue.
- Autosave with a debounce, a serialised queue, explicit 409 handling that replays pending edits
  on the newer revision, and truthful Saving / Saved / Save failed status.
- An exportable review summary: a print layout and a JSON download from the backend.
- Session deletion behind a confirmation, clearing frontend caches.

## What is fixture-backed

In `demo` mode, **everything**: the config, the session, the analysis job, the document bytes,
the explanations, the chat answers, the validation report and the export. The badge says so on
every screen. `fixtures/demo` is the only place those answers come from.

The **validation rules themselves** live in `fixtures/demo/src/validation.ts` and are
deterministic in both modes — they are rules read off the form, not a model's opinion.

## Demo controls

In demo mode only, a **Demo controls** dialog switches on real faults in the fixture backend:
next save fails, next save hits a 409, explanations and chat unavailable, session expired, slow
network. They exist so the recovery paths can be shown rather than described. Every one of them
is a working switch; there are no placeholder buttons anywhere in the UI.

## Limitations

Stated plainly, because a demo that overstates itself is worse than one that does less.

- **Demo mode analyses only the bundled sample.** Uploading a different PDF returns the
  "unsupported template" path rather than mapping the sample's fields onto a document it has not
  read. Analysing your own form needs live mode and the backend.
- **No backend is included here.** `live` mode needs a server implementing the contract in
  `packages/contracts`. The routes, names and shapes are fixed by that package.
- **FormFix never submits anything.** It does not fill the official PDF, does not talk to any
  portal, and cannot tell you whether an application will be accepted. The check says "No issues
  found by the configured checks" and nothing stronger.
- **Document readiness is self-reported.** The MVP collects no identity documents and verifies
  nothing.
- **Deletion promises only what the request returns.** Copies held by a provider or a backup are
  outside what this app can see.
- **Out of scope in this build** (and deliberately absent from the UI): photo ingestion,
  handwriting analysis, voice, WhatsApp, signatures, portal submission, and export of a
  completed official PDF.
- **Fonts load from Google Fonts** with local fallbacks (`Nirmala UI`, `Noto Sans`), so
  Devanagari and Telugu still render correct glyphs offline on most machines.
